# 위성/그림자 위치 예측 회전 편향 조사 보고서 (2026-08-31)

## 1. 요약

`SatelliteTracker`가 예측하는 위성·그림자 픽셀 위치에 실측 대비 체계적인 **회전(각도) 편향**이 존재함을 확인했다. 원인 후보를 하나씩 검증해서 대부분 배제했고, 실제로 존재하는 원인 하나(de-rotation 전/후 프레임 불일치)를 찾아 수정했으나 전체 편향의 약 10%만 개선됐다. **나머지 약 90%는 원인 불명 상태로 조사를 일시 중단**한다.

**⚠️ 범위에 대한 중요한 단서 (§12 참고)**: 이 편향은 **6개 세션 전부에서 확인된 게 아니다.** 그림자가 있는 4개 세션(2026-03-21/27/28, 2026-05-05 + 2026-04-17)의 전체 22개 창을 배경 대비 3-sigma 기준으로 전수 재검사한 결과, 신뢰할 만한 탐지가 나온 건 **2026-04-17(10개 중 7개)과 2026-03-21(5개 중 2개), 총 9개 창뿐**이었다. 이 9개 창에서 평균 +7.06°(2026-04-17만 보면 평균 7.93°, 2026-03-21만 보면 평균 4.02° — 세션 간 약 2배 차이). 나머지 3개 세션(2026-03-27 5개, 2026-03-28 2개, 2026-05-05 5개 창)은 그림자 자체가 배경과 거의 구분이 안 될 만큼 약해서(peak significance 0.8~1.4-sigma, 3-sigma 문턱에 한참 못 미침) **편향이 있는지조차 이 데이터로는 판단 불가능**하다 — "편향 없음"이 아니라 "측정 불가"다.

이 문서는 시도한 모든 가설, 검증 방법, 결과(성공/실패)를 시간순으로 상세히 기록한다. (§8: 외부 검토 라운드에서 제기된 "`pole_pa+np_ang`의 부호가 틀렸을 수 있다"는 최우선 가설을 포함한 추가 검증도 진행했으나, 순수 합성 테스트로 명확히 기각됐다 — 현재 공식은 정확하다. §10: 위성 본체도 물리적으로 신뢰 가능한 CH4 필터로 한정해 재분석하면 그림자와 같은 방향·비슷한 크기의 편향을 보여, 원인이 그림자 전용 코드가 아니라 위성·그림자가 공유하는 좌표 변환 경로에 있을 가능성이 유력해졌다.)

## 3. 조사 원칙 (제약 조건)

- **CV 기반 보정 절대 금지**: 위성/그림자의 이미지 내 실제 픽셀 위치를 감지(blob 탐지 등)해서 plate_scale, 위치 오프셋 같은 파라미터를 그 값에 맞춰 피팅/보정하는 방식은 이 프로젝트에서 여러 차례 명시적으로 금지됐다 (목성 표면의 다양한 형태 때문에 CV 신뢰도 자체가 낮다는 게 이유). 이번 조사도 이 원칙을 지켰다.
- **진단 목적의 CV는 허용**: "실제 위치가 어디쯤인지" 확인해서 어떤 가설이 맞는지 판단하는 데는 blob 탐지를 썼지만, 그 결과를 코드에 피드백해서 파라미터를 피팅하지는 않았다.
- **실제 수정은 순수 물리/수학/기하학적 근거로만**: 최종적으로 적용한 수정(§7)은 CV 데이터에 근거한 게 아니라, "마커를 찍는 이미지에서 각도를 재야 한다"는 순수 논리적 근거로 이루어졌다.

---

## 4. 배경: 좌표 변환 공식

`SatelliteTracker`는 위성/그림자의 하늘 좌표(적경차 `dra_arcsec`, 적위차 `ddec_arcsec`)를 다음 공식으로 이미지 픽셀 좌표로 변환한다 (`pipeline/modules/satellite_tracker.py`):

```
east_px  = ew_sign * dra_arcsec  / plate_scale
north_px = ns_sign * ddec_arcsec / plate_scale
pa_rad   = radians(pole_pa_deg + np_ang_deg)
dx_px    = east_px * cos(pa_rad) + north_px * sin(pa_rad)
dy_px    = east_px * sin(pa_rad) - north_px * cos(pa_rad)
```

- `pole_pa_deg`: 이미지 자체에서 벨트 방향을 측정해서 얻는 값 (`auto_detect_equator_pa()`, `pipeline/modules/derotation.py`)
- `np_ang_deg`: JPL Horizons에서 조회하는 목성 극축의 천구상 위치각(North Pole angle)
- `plate_scale`: 디스크 반지름(px)과 목성의 각반경(Horizons)으로부터 산출하는 "/px 값

그림자는 별도로 태양-위성-목성 3D 광선추적(oblate spheroid ray intersection, `_shadow_pos_skyfield()`)을 거쳐 목성 표면 좌표를 구한 뒤 같은 공식으로 픽셀 변환한다.

## 5. 시도한 가설과 결과 (시간순)

### 5-1. Jupiter/Ganymede 본체 천체력 정확성 — ✅ 결백 확인

**방법**: Skyfield(jup365.bsp)로 계산한 Jupiter·Ganymede의 겉보기 RA/Dec를 JPL Horizons 실시간 조회(target 599, 503, observer 500@399)와 직접 대조.

**결과**: 2026-04-17T10:39:42Z 기준 소수점 5자리까지 완전 일치 (Jupiter: 108.32570 vs 108.32569, Ganymede: 108.31292 vs 108.31292). 광행시간 보정, 커널 데이터, 기본 천체력 계산 파이프라인은 문제 없음.

### 5-2. 오블레이트 구체 그림자 광선추적 수식 — ✅ 결백 확인

**방법 1 (수치 검증)**: `_shadow_pos_skyfield()`의 이차방정식 closed-form 해(λ_near)를, λ를 아주 촘촘히(20만 스텝) 스캔하며 부호가 바뀌는 지점을 직접 찾는 브루트포스 수치탐색과 대조.

**결과**: λ=1.001293으로 소수점 6자리까지 정확히 일치. 대수적 구현에 오류 없음.

**방법 2 (합성 엣지케이스)**: 위성을 태양-목성 직선상에 정확히 놓은 가상의 시나리오를 만들어, 이때 그림자가 반드시 "sub-solar point"(태양 바로 아래 지점)와 같은 위도에 떨어져야 한다는 물리적 필연성을 이용해 검증.

**결과**: 광선추적으로 계산한 그림자 위도(1.0433011063052866°)가 독립적으로 계산한 sub-solar 위도(1.0433011063162845°)와 10자리 유효숫자까지 일치. 오블레이트 구체 교차 계산 자체는 완전히 정확함.

**부가 발견 (버그 아님)**: 실제 데이터에서 그림자의 목성면 위도가 위성 자신의 궤도위도(~0°)나 sub-solar 위도(~1.2°)와 크게(~-17°) 다르게 나온 사례가 있었는데, 이는 버그가 아니라 위성-목성 간 약 100만km를 진행하는 동안 태양-위성 직선의 ~1° 기울기가 누적되는 정상적인 물리 현상임을 위 검증으로 확인했다.

### 5-3. `np_ang_deg` 값 자체 — ✅ 결백 확인

**방법**: JPL Horizons quantity 17(North Pole 위치각)을 실시간 조회해서 저장된 값과 대조.

**결과**:
| 세션 | Horizons 조회값 | 저장된 값 |
|---|---|---|
| 2026-04-17 | 8.7317° | 8.7318° |
| 2026-03-21 | 7.8635° | 7.8637° |

소수점 4자리까지 일치. `np_ang_deg`는 원인이 아님.

### 5-4. disk 중심 좌표 기준점 불일치 — ✅ 배제

**방법**: 진단 스크립트가 사용하던 disk 중심(로그에 저장된 값)과 `aperture_contrast.py`가 실제로 쓰는 disk 중심(매 필터마다 `find_disk_center()`를 새로 호출해서 얻는 값)이 다를 가능성을 의심해, 정확히 같은 호출로 재계산해서 비교.

**결과**: 각도 편차가 그대로 재현됨 (예: window_01 +9.07°→+9.14°, 오차범위 내 동일). 기준점 문제 아님.

### 5-5. `auto_detect_equator_pa()` 알고리즘 자체의 편향 — ✅ 결백 확인

**배경**: 기존에 있던 회귀 테스트(`test_auto_detect_equator_pa_matches_warp_sign_convention`)는 부호만 확인(`<-5`/`>5`)하고 몇 도 단위의 편향은 검증하지 않는다는 걸 확인했다.

**방법**: 각도를 정확히 알고 있는 이상적인 합성 벨트 이미지(사인파 패턴, 원형 디스크)를 cv2로 여러 각도(±2°~±20°)로 회전시켜 `auto_detect_equator_pa()`가 정확히 복원하는지 테스트.

**결과**: 편향이 방향성 없이 작게 흩어짐(+0.5°~-4°, 부호 일관성 없음) — 알고리즘 자체는 이상적 조건에서 편향이 없다.

### 5-6. Limb-darkening 오염 — 단순 모델 — ✅ 가설 반박됨

**배경 가설**: 코드 자체 주석에 "coarser scale을 쓰면 limb-darkening 오염으로 ~10° 편향이 생긴다"는 기존 경고가 있고, 실측 편향의 부호가 이 오염 방향과 일치해서 유력한 후보로 봤다.

**방법**: 원형 디스크 + 사인파 벨트에 실제 목성처럼 가장자리가 어두워지는 곱셈형 Minnaert 모델 오염(`I_obs = I_belt * cos(theta)^m`, m=0.3~1.0)을 입혀서, production이 실제로 쓰는 fine+belt wavelet scale로 측정.

**결과**: 오염 강도를 아무리 올려도(m=0.3~1.0) 편향이 거의 늘지 않음(평균 |bias| 1.4~1.7° 유지, 오염 없을 때와 거의 동일). Minnaert 나눗셈(flattening) 보정을 적용해도 개선 없음(±0.5° 잡음 수준 이내 차이). **가설 반박됨.**

### 5-7. Limb-darkening 오염 — 현실적 모델 — ✅ 가설 재반박됨

**방법**: 실제 목성에 더 가깝게 조건을 강화 — 목성의 실제 편평도(오블레이트, semi_b/semi_a=0.935), 사인파가 아닌 날카로운 불규칙 다중 벨트(tanh 엣지), 실제 노이즈, `find_disk_center()`가 만들법한 disk 중심(+3,-2px)·반지름(-5%) 오차까지 개별 및 조합으로 테스트.

**결과**:
- 정확한 기하 조건(노이즈 없음): 오블레이트+불규칙 벨트를 넣어도 평균|bias| 0.7~0.9°로 여전히 무의미.
- 중심/반지름 오차만 추가: 마찬가지로 무의미.
- 현실적 노이즈(σ=0.02) 추가: 오차가 폭발(평균|bias|~23°, 개별 값 ±40° 요동)했지만 **방향성 없는 랜덤 잡음**이었지(mean_bias는 0 근처), 실측처럼 일관되게 양수인 편향이 아니었음.

**결론**: 오블레이트, 불규칙 벨트, disk 피팅 오차, 노이즈 중 어느 것도(단독이든 조합이든) 실측과 같은 **일관된 방향성** 편향을 재현하지 못함. pole_pa **측정** 단계 자체는 이렇게 현실적으로 스트레스를 줘도 범인이 아니다.

### 5-8. de-rotation 전/후 프레임 불일치 — ✅ 실제 원인 발견 (부분적)

**가설**: `pole_pa_deg`는 de-rotation **이전**의 원본(raw) 프레임에서 측정되는데(`_scan_session_pole_pa`), 실제 위성/그림자 마커는 de-rotation으로 워프·스택된 **최종 출력** 이미지에 찍힌다. 두 이미지가 미세하게 다른 방향을 가리킬 수 있다.

**방법**: 같은 `auto_detect_equator_pa()`를 de-rotation 이전 원본과 이후 산출물(derotated TIF) 양쪽에 직접 적용해서 비교. CV 없이 순수 재측정.

**결과**: 실제로 차이가 존재함 — 2026-04-17: 대부분 +0.5°~+2.5° (한 건 +3.5°, 한 건 -0.5°), 2026-03-21: window_01은 +1~+3°, window_02는 거의 0. **방향은 대체로 실측 편향과 일치.**

**결론**: 진짜 원인이지만 **부분적**(전체 편향의 1/4~1/2 수준만 설명).

### 5-9. 적용한 수정 — `pipeline/steps/derotate_stack.py`

`derotate_window()`로 de-rotation을 마친 직후, 산출된 창(window)의 대표 필터(우선순위 IR→R→G→B→CH4) 결과물에서 `pole_pa_deg`를 다시 측정해서 `pole_pa_for_tracker`라는 새 값으로 저장하고, 이 값을 위성/그림자 tracker(`sat_log`, `_apply_satellite_composite`)에 사용하도록 변경했다. de-rotation 워프 자체를 만드는 데 쓰는 `pole_pa_for_warp`(원본 프레임에서 측정, 세션 전체 공용)는 그대로 둬서, **워프 품질에는 아무 영향이 없다** (테스트 157개 전부 통과 확인).

**실측 개선 효과** (6개 세션 재처리 후 동일 방식으로 재측정):

| | 회전 편향 평균 | 픽셀 오차 평균 |
|---|---|---|
| 수정 전 | +8.35° | 9.56px |
| 수정 후 | +7.48° | 8.84px |

**약 8~10% 개선**. 위성(satellite) 쪽은 거의 변화 없음(-26.8°→-28.6°, 데이터 2개뿐이라 잡음 가능성 높음).

**주의**: 이 수정으로 모든 창(window)이 똑같이 개선되는 건 아니다. 사용자가 처음 지적했던 `window_01`은 하필 대표 필터(IR)의 de-rotation 전/후 값이 우연히 정확히 같아서(-13.0° = -13.0°) **변화가 전혀 없다**. 반면 `window_04`는 -13.0°→-9.5°로 가장 크게 바뀌었다.

### 5-10. 경위대(alt-az) field rotation 가설 — ✅ 배제

**가설**: 마운트가 경위대 방식이면 추적 중 시야 자체가 서서히 회전(field rotation)하는데, 창 내 여러 프레임을 스택할 때 이를 보정 안 하면 스택된 최종 이미지의 벨트 각도가 개별 원본 프레임과 달라질 수 있다.

**확인**: 사용자에게 직접 질의 → **적도의(equatorial) 마운트로 확인됨**. 가설 기각.

### 5-11. 극축 정렬 오차 누적 drift 가설 — ✅ 배제

**가설**: 적도의 마운트라도 극축 정렬이 완벽하지 않으면 세션 전체에 걸쳐(수 시간) 서서히 field rotation이 누적될 수 있다.

**방법**: 2026-04-17 세션(10:39~12:55, 약 2.3시간)의 창별 재측정 pole_pa 값을 시간순으로 나열:

```
-13.0 → -11.0 → -11.5 → -9.5 → -13.5 → -13.0 → -13.5 → -15.5 → -11.0 → -11.0
```

**결과**: 단조 증가/감소 패턴이 전혀 없이 왔다갔다 함. 극축오차 누적이라면 시간에 따라 한 방향으로 서서히 변해야 하는데 그렇지 않음 — 실제 물리적 drift라기보다 창마다 3프레임만으로 측정하는 데서 오는 **측정 잡음**(이전 정밀도 조사에서 확인한 표준편차 1.4~2.6°대와 부합)에 가깝다. 가설 기각.

### 5-12. 독립 대조 도구 검토 (WinJUPOS / IMCCE) — 시도 불가 / 무의미

- **WinJUPOS**: Windows 전용 프로그램이라 현재 Linux 환경에서 사용 불가.
- **IMCCE Miriade** (프랑스 천문대의 리눅스 친화적 웹 API, [https://ssp.imcce.fr/webservices/miriade/](https://ssp.imcce.fr/webservices/miriade/)): 확인해보니 위성 **본체** 위치 천체력만 제공하고 **그림자 좌표**를 직접 계산해주는 기능은 없음. 본체 위치는 이미 §5-1에서 JPL Horizons와 정확히 일치함을 확인했으므로, IMCCE로 다시 대조해도 같은 결론만 반복될 뿐 새로운 정보를 얻을 수 없다고 판단해 진행하지 않음.

## 7. 최종 상태

- **원인이 확인되어 수정 반영된 부분**: de-rotation 전/후 프레임 불일치 (~1-3°, 전체 편향의 8~10% 개선). 코드: `pipeline/steps/derotate_stack.py`의 `pole_pa_for_tracker`.
- **여전히 원인 불명**: 남은 ~7°대(전체의 대부분) 회전 편향.
- **왜 중요한가**: 이건 진단 이미지만의 문제가 아니라 실제 위성/그림자 **합성(제거) 위치 자체**가 틀어진다는 의미다. 전형적인 transit 반경에서 남은 픽셀 오차(~9px)가 객체 자체 반경(~6~11px)과 맞먹는 수준이라, 실제 합성 품질에 영향을 줄 수 있다.
- **투입한 데이터 한계**: 검증 가능한 데이터는 6개 세션, 그중 유효 지점(그림자 8개 + 위성 2개)뿐이며 전부 소진했다. 추가 세션 데이터가 없는 한 이 방향의 순수 formula 검증은 한계에 도달했다고 판단한다.

## 8. 외부 검토 의견 평가 (2026-08-31 추가)

이 보고서를 본 다른 세션(외부 검토자)이 의견을 줬다. 검토자에게 전달된 코드가 구버전(이번 조사에서 적용한 수정들 이전, 그리고 훨씬 이전에 이미 고쳐진 CV 자동보정 제거·flip_ns 로직도 반영 안 된 버전)이었기 때문에, 코드 스니펫은 참고하지 않고 **아이디어만** 현재 코드 기준으로 하나씩 검증했다.

### 8-1. 최우선 가설: `pole_pa_deg + np_ang_deg`가 아니라 `- np_ang_deg`여야 한다 — ❌ 검증 결과 기각

**검토자 주장**: 카메라 회전각(`camera_pa`)은 `image_pole_pa - NP.ang`이어야 하는데 현재 코드는 `+`를 쓰고 있어 부호가 틀렸을 수 있다.

**검토자가 직접 제안한 검증 방법**(§3, "CV 없이 검증할 수 있는 결정적 단위 테스트")을 그대로 구현해서 실행했다: 천구상 East/North 벡터를 가상의 카메라 회전각으로 투영하고, 그 결과로부터 "이미지에서 측정됐을 pole_pa"를 역산한 뒤, `pole_pa - np_ang`과 `pole_pa + np_ang` 중 어느 쪽이 원래 카메라 회전각을 복원하는지 확인하는 방식이다 (`experiments/verify_pole_pa_plus_minus_np_ang.py`).

서로 다른 (NP.ang, 카메라 회전각) 조합 12가지에 대해 `+`/`-` × `ew_sign`/`ns_sign` 8가지 조합을 전부 테스트한 결과:

| 조합 | 일치한 시나리오 수 |
|---|---|
| **`+np_ang`, ew=-1, ns=+1** | **11/12** (실패한 1건은 극단적 카메라 기울기에서 생기는 정상적인 ~4° 측정잡음 때문에 임계값을 살짝 벗어난 것) |
| `-np_ang`, ew=-1, ns=+1 (동일 ew/ns) | 1/12 (NP.ang=0으로 두 공식이 수학적으로 동일해지는 자명한 경우뿐) |
| 그 외 모든 조합 | 0/12 |

**결론**: 현재 프로덕션 공식(`+ np_ang_deg`)이 명확히 맞다. `-` 가설은 기각됐다.

부가적으로, `spherical_derotation_warp()`의 기존 docstring에 이미 다음 문구가 있었다: *"Do not feed NP.ang into this function directly; earlier revisions of this docstring incorrectly implied you should, which independently misled two rounds of external code review"* — 즉 `pole_pa_deg`와 `NP.ang`을 혼동하는 유형의 실수가 이 프로젝트에서 **이미 두 차례 반복된 전례**가 있다. 이번 검토자의 가설도 같은 유형의 개념 혼동일 가능성이 높다는 정황 증거다.

### 8-2. CV 기반 plate_scale 자동보정이 여전히 실행 중이라는 지적 — ❌ 구버전 코드였음, 현재는 이미 제거됨

검토자가 인용한 `_auto_calibrate_plate_scale()`, `set_plate_scale_calibration()`, `_cx_offset` 관련 코드는 이번 조사 훨씬 이전에(§ "CV 기반 위치 보정 금지" 원칙이 확립될 때) 이미 완전히 제거됐다. 현재 코드에서 검색해도 제거 사실을 알리는 docstring 문구 한 줄 외에는 아무것도 안 나온다:

(19번 줄은 "이 기능을 왜/언제 제거했는지" 설명하는 모듈 docstring일 뿐, 실제 함수는 없음.)

### 8-3. §5-9의 `pole_pa_for_tracker` 수정이 반영 안 됐다는 지적 — ❌ 구버전 코드였음, 현재는 반영되어 있음

### 8-4. `tracker_flip_ns`가 `derot_flip`으로 fallback된다는 지적 — ❌ 구버전 코드였음, 이미 더 이전에 (2026-08-29) 고쳐짐

현재 `resolve_tracker_flip_ns()`(`pipeline/steps/satellite_composite.py`)의 docstring에 이미 명시돼 있다:

> "NOTE: this must NOT fall back to derot_flip... Confirmed by real-data audit (2026-08-29): sessions that took this fallback produced satellite/shadow position errors up to ~60px... while sessions resolved via belt-asymmetry auto-detect matched real transit positions to within a few px."

즉 검토자가 지적한 바로 그 문제가 이미 실측으로 확인되고 고쳐진 이력이 있다(이번 회전편향 조사보다 이전 시점). 현재는 명시적 설정값 → belt-asymmetry 자동감지 → (둘 다 실패시) 위성 추적 자체를 skip, 순서로 처리하며 `derot_flip`은 전혀 관여하지 않는다.

### 8-5. de-rotation warp가 실제 회전이 아니라 PA 추정기만 흔드는 걸 수도 있다는 지적 — ⚙️ 검증해서 부분적으로 맞음, §5-9 해석을 다듬음

검토자가 제안한 "Test A"(§6-2, latitude-only 패턴으로 warp 불변성 확인)를 그대로 구현해서 실행했다 (`experiments/verify_warp_preserves_pole_pa.py`): 경도(longitude) 방향 변화가 전혀 없는(순수 위도 함수) 합성 벨트 패턴을 만들어, `spherical_derotation_warp()`에 다양한 pole_pa(0°/±13°/45°)·dt_sec(0~600초)·편평도(1.0/0.935) 조합으로 통과시킨 뒤 전/후 pole_pa를 비교했다.

**결과**: 모든 조합에서 변화가 0~±0.5°에 그쳤다 — 이는 `auto_detect_equator_pa()`의 히스토그램 해상도(0.5°) 양자화 오차 수준일 뿐, 유의미한 변화가 아니다. **즉 warp 자체(순수 경도방향 shear)는 pole_pa를 바꾸지 않는다** — 검토자의 우려(warp가 진짜 회전이 아닐 수 있다)는 사실이지만("warp는 rigid rotation이 아니라 위치의존적 shear"), 그렇다고 해서 §5-8/5-9에서 실측한 de-rotation 전/후 pole_pa 차이(~1-3°)가 "가짜"라는 뜻은 아니다.

**해석 수정**: §5-8/5-9는 "warp가 좌표계를 회전시킨다"는 표현을 썼는데, 이번 검증으로 그건 정확한 설명이 아님이 드러났다. 더 정확한 설명은: 실제 세션은 이상적인 위도-only 패턴이 아니라 **경도 방향 구조(폭풍, 벨트 폭 변화 등)가 있는 실제 벨트**를 여러 프레임(창당 3장) 스택해서 만드는데, 이 과정에서 각 프레임의 실제(경도 의존적) 벨트 구조가 조금씩 다르게 shear되고 합쳐지면서 최종 합성본의 겉보기 벨트 기울기가 원본 단일 프레임과 달라질 수 있다는 것이다. 즉 원인은 "warp의 좌표계 회전"이 아니라 "실제 벨트 구조 + 다중 프레임 스택 + shear의 상호작용"이다. **수정 자체(§5-9, 실제로 마커를 찍는 이미지에서 pole_pa를 재측정)는 이 정정된 설명 하에서도 여전히 정당하다** — 이유가 무엇이든, 최종 출력 이미지의 실제 벨트 방향에서 각도를 재는 게 사전 단일 프레임 값을 재사용하는 것보다 낫기 때문이다. 다만 "왜 그 차이가 생기는지"에 대한 §5-8의 설명은 이번 검증으로 더 정확해졌다.

### 8-6. plate_scale이 세션당 한 번만 캐시된다는 지적 — 별도 이슈, 이번 회전편향과는 무관 (미검증)

검토자는 `SatelliteTracker.get_plate_scale()`이 최초 호출 시 캐시되는데, 실제로는 창(window)·필터마다 `disk_radius_px`가 조금씩 다르게 측정된다는 점을 지적했다. 이건 **스케일(반경) 문제이지 회전 문제가 아니라서** 지금까지 조사한 회전 편향(+5~14°)과는 직접 관련이 없다고 판단해 이번 조사에서는 검증하지 않았다. 별도로 짚어볼 가치가 있는 지적이지만 우선순위는 낮다고 본다.

## 9. 잔차-이동방향 상관관계 분석 (2026-08-31 추가, 두 번째 외부 검토 후속)

두 번째 외부 검토 라운드에서 앞의 §8 지적 대부분(부호, CV 자동보정, `pole_pa_for_tracker`, `tracker_flip_ns` fallback)을 구버전 기준이었다고 스스로 철회하면서, 새로 "출력 이미지의 유효 촬영 시각(effective stack time)이 `center_time`과 다를 수 있다"는 가설을 제시했다. 이건 §5의 반경/각도 분해 방법론 자체의 맹점을 짚은 통찰이었다 — "접선 방향 오차"로 분류한 것이 사실은 "시간 오차로 인해 객체가 자기 궤도 방향으로 밀린 것"일 수 있다는 지적이다.

### 9-1. 기하학적 타당성 확인

그림자의 실제 이동 속도 벡터(같은 검증된 ephemeris 코드로 t, t+60초의 위치차를 계산 — CV 아님)를 계산해보니, 8개 그림자 지점 전부에서 접선 성분이 반경 성분과 비슷하거나 더 큰 크기였다(`experiments/verify_...` 계열 대신 인라인 스크립트로 확인, 문서에는 결과만 기록). 즉 "접선처럼 보이는 오차가 사실 시간 오차일 수 있다"는 전제 자체는 기하학적으로 타당했다.

### 9-2. "quality-weighted 평균 시각" 자체는 원인이 아님

검토자가 제안한 방법대로, 각 window의 실제 로그에 있는 프레임별 `dt_sec`/`norm_score`(weight)로 실제 weighted-mean 촬영시각을 계산해서 `center_time`과 비교했다 (CV 없이 순수 로그 데이터 산술). 결과: 차이가 최대 2분(대부분 30초 이내)에 불과해, 필요한 시간차(아래 9-3)를 설명하기엔 너무 작았다.

### 9-3. 잔차 벡터와 실제 이동방향의 상관관계 — 놀라울 정도로 깨끗한 패턴, 원인 미상

잔차 벡터(실측 위치 − 예측 위치, 2D 전체 벡터)와 객체의 실제 순간 이동방향(velocity, 같은 tracker 코드로 t/t+60초 위치차 계산) 사이의 각도를 계산했다:

| 종류 | 지점 수 | 잔차-이동방향 각도 | 해석 |
|---|---|---|---|
| 그림자 (shadow) | 8/8 | **151.8° ~ 176.5°** (거의 정반대) | 마치 실제 위치가 예측보다 몇 분 "과거"에 있는 것처럼 보임 |
| 위성 본체 (satellite) | 2/2 | 79.7°, 89.1° (거의 수직) | 그림자와 다른 패턴 (단, 표본 2개뿐, 반경도 작아 잡음 가능성 있음) |

그림자 8개 전부가 150~177° 범위(180°=완전 반대)에 몰려 있는 건 우연으로 보기 어렵다. 필요한 "시간 지연"을 역산하면 세션마다 다음과 같다:

| 세션 | 필요 시간 지연 |
|---|---|
| 2026-04-17 (6개 창) | 4.7 ~ 8.4분 |
| 2026-03-21 (2개 창) | 1.8 ~ 2.9분 |

### 9-4. 가장 유력한 설명(노출 타임스탬프 의미)을 사용자에게 확인 → 기각됨

파일명 타임스탬프(FireCapture 패턴, 예: `2026-04-17-1039_7-...`)가 비디오 캡처의 시작/중앙/끝 중 무엇을 뜻하는지, 필터 하나당 캡처가 보통 얼마나 걸리는지 사용자에게 직접 확인했다. **답변: 캡처 중앙(대표) 시각 기준, 필터당 30초~2분.** 이 정도 캡처 길이로는 최대 1분(절반)의 오차만 가능하므로, 필요한 1.8~8.4분을 설명하기엔 자릿수가 안 맞는다. **이 가설은 기각.**

### 9-5. 현재 상태 (수정 전): 원인 미상이지만 매우 구체적인 단서

- 그림자에서만(위성 본체는 다른 패턴) 나타나는, "몇 분의 시간 지연"처럼 보이는 매우 일관된(8/8) 기하학적 서명이 확인됐다.
- 광행시간(LTT) 보정 크기(~44분, Earth-Jupiter)는 Horizons와의 본체 위치 완전 일치로 이미 간접 검증됐고, 그림자 계산의 sun/jupiter/moon 위치를 모두 동일 `t_emit`에서 평가하는 방식도 §5-2의 on-axis 합성 테스트로 이미 정확함이 확인됐다 — 그런데도 이 패턴이 왜 생기는지는 못 찾았다.
- 위성 본체(2개, 노이즈 많음)는 그림자와 다른(수직에 가까운) 패턴을 보여, 원인이 그림자 계산(`_shadow_pos_skyfield`)에 특정된 것일 가능성을 시사하지만 확정하기엔 표본이 부족하다.
- 이 상관관계 자체는 CV 없이(로그 데이터 산술 + 검증된 ephemeris 코드로 속도 계산) 얻은 결과이므로 진단으로는 유효하지만, 근본 원인 규명에는 실패했다.

## 10. 위성 vs 그림자 비교의 근본적 재검토 (2026-08-31 추가, 세 번째 논의)

사용자가 "위성과 그림자는 원래 disk상 다른 위치에 찍히는 게 정상 아니냐"고 지적하면서, §9-5의 "위성은 그림자와 다른 패턴" 비교 자체의 타당성을 재검토하게 됐다.

### 10-1. 확인된 confound: "잔차-이동방향 각도" 비교는 위치에 따라 달라짐

시계 비유로 설명: disk를 시계판이라 하면, "모든 객체를 시계방향으로 살짝 미는" 공통 버그가 있어도, 12시 방향 객체는 오른쪽으로, 3시 방향 객체는 아래쪽으로 밀리는 것처럼 보인다 — 같은 버그인데 위치에 따라 겉보기 방향이 다르다. 실제로 2026-03-28 window_05를 확인해보니 위성(Io)은 disk 중심 기준 -137.6°, 그림자(Io_shadow)는 -7.2°로 130.5° 떨어진 완전히 다른 위치에 있었다(이미지로도 확인: 위성은 왼쪽 위, 그림자는 오른쪽). 반면 이 둘의 실제 이동 속도 방향은 0.2~0.5° 차이로 거의 동일했다(같은 위성의 궤도운동이 원인이므로 당연함).

**결론**: "잔차가 이동방향과 이루는 각도"를 위성과 그림자 사이에서 직접 비교하는 건 잘못된 방법이다 — disk상 위치가 다르면 공통 버그라도 다르게 보인다. §9-3~9-5의 이 비교로 "그림자 전용 문제"라고 판단한 건 근거가 불충분했다.

### 10-2. 위치-불변(position-invariant) 비교로 재설계

올바른 비교 기준은 disk 중심 기준 각도 편향(δ, §5-8/5-9/§8-1에서 원래 쓰던 지표) 그 자체다 — 이건 "시계방향으로 미는 정도"에 해당하는 값이라, 공통 버그라면 위치와 무관하게 위성/그림자 둘 다 비슷한 값이 나와야 한다는 예측을 할 수 있다.

### 10-3. 워크플로우로 재검증: 그림자는 재확인, 위성은 애초에 데이터가 없었음

두 개의 서브에이전트를 병렬로 돌려, 기존의 단순 argmin/argmax 방식보다 훨씬 엄격한 방법(배경 대비 3-sigma 유의성 임계값 + 2~5r 4가지 탐색범위에서의 안정성 확인)으로 그림자 8곳과 위성 6곳(기존 2곳 + 이전에 "잡음일 수 있다"고 의심했던 4곳 포함)을 독립적으로 재측정했다.

**그림자 결과**: 새 방법으로도 δ 평균 +7.47°, 중앙값 +8.31°, 표준편차 2.60° — 기존 단순 방법(+7.48°/+8.04°/2.66°)과 사실상 동일했다. 서로 다른 두 탐지 방법이 이렇게 일치한다는 건 그림자 편향 신호 자체가 진짜라는 강한 방증이다.

**위성 결과**: **6곳 전부 "신뢰도 낮음(low)"**. IR/R/G/B 등 일반 필터에서 배경 대비 유의성이 1.1~1.9-sigma에 그쳤고(3-sigma 문턱 근처도 못 감), 탐색 범위를 2r→5r로 넓혀도 이 값이 전혀 변하지 않았다 — 이는 "약한 신호"가 아니라 "애초에 유의미한 신호가 없다"는 뜻이다(순수 잡음 수준에서 평평함). CH4 필터에서만 몇몇 창에서 근소하게(3.0~3.3-sigma) 문턱을 넘었지만 단일 필터일 뿐이라 확정할 수 없다. 물리적으로도 설명된다: 위성 본체는 목성 자신의 밝은 구름 위를 지나가므로 배경 대비가 원래 약하고(그림자는 반대로 어두운 점이라 대비가 강함), CH4는 목성 원반 자체가 메탄 흡수로 어두워지는 특성상 예외적으로 대비가 생긴다.

### 10-4. 최종 결론: §9-5의 "그림자 전용" 판단은 근거 자체가 무효였음

이전에 "위성이 그림자와 다른(수직에 가까운) 패턴을 보인다"고 한 관측 자체가, 사실은 **애초에 신뢰할 수 있는 위성 탐지가 하나도 없었기 때문**(순수 잡음을 마치 신호처럼 다룬 것)임이 드러났다. 즉:

- 그림자 편향(+5~14°)은 두 가지 독립된 방법으로 재확인됐고 확실히 실재한다.
- 위성 쪽엔 6개 세션 어디에도 신뢰할 만한 실측 데이터가 없다(견고한 방법으로도 마찬가지).
- **따라서 "그림자 전용 버그인지 공통(위성도 포함) 버그인지는, 지금 가진 6개 세션 데이터로는 원천적으로 판단 불가능하다.** 비교 대상이 될 신뢰할 만한 위성 데이터 자체가 없기 때문이다. §9-5의 "그림자 전용일 가능성" 판단은 철회한다.
- `_shadow_pos_skyfield`를 그림자 전용 문제로 단정하고 파고드는 건 근거 없는 가정이 될 수 있으므로, 재개 시에는 "그림자와 위성이 공유하는 pole_pa+np_ang 경로" 쪽도 동등하게 의심해야 한다.

### 10-5. CH4 한정 재분석 (사용자 제안) — 위성도 그림자와 같은 방향·비슷한 크기의 편향을 보임

사용자가 "위성은 CH4를 뺀 나머지 필터에서 신호가 약하거나 없을 수 있으니, 신뢰할 데이터를 CH4로 한정하면 된다"고 제안했다. §10-3에서 이미 확인했듯 CH4는 물리적으로 타당한 예외다(목성 원반 자체가 메탄 흡수로 어두워지는 반면 위성은 그렇지 않아 대비가 생김). 워크플로우 결과에서 CH4가 3.0-sigma 문턱을 넘긴(peak_sig>=3.0, "medium" 신뢰도) 4개 창만 추려 δ를 다시 계산했다:

| 세션 | 창 | 객체 | |pred| | |CH4위치| | δ (각도편향) | 총 오차(px) |
|---|---|---|---|---|---|---|
| 2026-03-28 | window_05 | Io | 27.2px | 22.9px | **+1.83°** | 4.4px |
| 2026-05-05 | window_01 | Europa | 22.6px | 20.1px | **+11.60°** | 5.0px |
| 2026-05-05 | window_02 | Europa | 36.2px | 31.0px | **+4.96°** | 6.0px |
| 2026-05-05 | window_03 | Europa | 53.0px | 47.7px | **+2.04°** | 5.6px |

평균 **+5.11°**, 중앙값 +3.50°, 표준편차 3.95° (표본 4개, 반경이 작아 §10-3처럼 잡음에 취약함은 여전히 감안해야 함). 참고로 그림자 8개는 평균 +7.47°, 중앙값 +8.31°.

**해석**: CH4 한정 위성 데이터 4개 전부 **그림자와 같은 부호(+), 비슷한 자릿수(한 자릿수 도)**로 나왔다. 4/4가 모두 양수라는 것도(반지름이 작아 잡음이 크다는 점을 감안해도) 순전히 우연으로 보기는 어렵다. §10-4에서 "위성 비교 자체가 불가능하다"고 했던 결론을 다음과 같이 수정한다:

- **이전(§9-5, §10-4) 결론 철회**: "위성이 그림자와 다른 패턴을 보인다" → 근거였던 데이터가 잡음이라 철회했음.
- **이번(§10-5) 결론**: 물리적으로 타당하게 신뢰 가능한 위성 데이터(CH4)로 다시 보니, 오히려 **그림자와 같은 방향·비슷한 크기의 편향을 보인다** — 표본이 작다는 한계는 있지만, 이건 "그림자 전용 버그"보다 **"위성·그림자가 공유하는 pole_pa_deg+np_ang_deg → 픽셀 변환 경로에 공통 원인이 있다"**는 가설을 지지하는 방향이다.
- `_shadow_pos_skyfield`(그림자 전용 3D 광선추적)는 이미 §5-2에서 수치·합성 검증으로 결백이 확인된 부분이므로, 공통 경로 가설과 결합하면 **남은 유력 용의자는 그림자/위성이 공유하는 pole_pa_deg 측정치 자체, 또는 그 값을 pole_pa_deg+np_ang_deg로 결합해 픽셀에 투영하는 공통 단계**로 좁혀진다 (단, §8-1에서 이 결합 공식의 부호(+/-)는 이미 합성 테스트로 검증됐음 — 부호가 아니라 **크기/오프셋** 쪽에 남은 문제가 있을 가능성).

### 10-6. 표본 확대(n=4→5) 및 통계적 재평가 — 방향은 지지되나 크기는 불확실

2026-03-28 window_01/02/03, 2026-05-05 window_04/05/06 — 아직 안 본 위성 창 6개를 CH4로 동일한 견고한 방법으로 추가 확인했다. 5개 중 4개는 여전히 3-sigma 문턱을 못 넘었고, **2026-05-05 window_04만 추가로 통과**(peak_sig 3.13-3.44, 안정적 centroid). 이 창의 δ는 **+0.08°** — 사실상 0에 가깝다.

n=5 최종: +1.83°, +11.60°, +4.96°, +2.04°, **+0.08°** → 평균 +4.10°, 중앙값 +2.04°, 표준편차 4.06°.

95% 신뢰구간(정규근사): **[+0.12°, +8.08°]**.

- **0(편향 없음)은 이 구간에서 간신히 벗어난다** → 위성 쪽에도 우연이 아닌 실제 편향이 있을 가능성이 (통계적으로, 근소하게) 지지된다.
- **그림자의 +7.47°는 이 구간 안에 포함된다** → "위성·그림자가 같은 크기의 공통 편향을 공유한다"는 가설도 이 데이터로는 배제되지 않는다.
- 그러나 표본이 여전히 작고(n=5) 개별 값의 편차가 크며(0.08~11.60°), 점추정치(평균 +4.10°)는 그림자(+7.47°)보다 뚜렷이 작다 — "정확히 같은 크기"라고 확정할 근거는 아니다.

**재평가한 결론**: §10-5의 "공통 원인 가설 지지"는 완전히 뒤집히진 않았지만 톤을 낮춰야 한다 — **"위성에도 방향이 같은(양의) 편향이 있을 가능성이 통계적으로 그럴듯하지만, 그림자와 정확히 같은 크기인지는 이 데이터로 확정할 수 없다"**가 더 정확한 요약이다. 6개 세션의 위성 관련 창(2026-03-28, 2026-05-05 전체 12개 창, CH4 포함 전체 필터)을 모두 확인했으므로, 이 데이터셋에서 더 뽑아낼 수 있는 위성 데이터는 없다.

## 11. 공통 경로("pole_pa_deg + np_ang_deg → 픽셀") 직접 조사 (2026-08-31 추가, 네 번째 논의)

§10에서 "공통 경로 쪽이 유력하다"는 방향이 나온 뒤, 실제로 그 공통 경로 자체를 더 깊이 팠다. 결과: **여기서도 구체적인 버그를 찾지 못했다** — 배제 목록만 늘었다.

### 11-1. body/shadow 픽셀 투영 코드 직접 대조

`_get_positions_skyfield()`(위성 본체)와 `_icrf_to_px()`(그림자, `_shadow_pos_skyfield` 내부)의 좌표변환 코드를 한 줄씩 나란히 대조했다:
```
dra_arcsec  = dra_deg * cos(radians(ref_dec)) * 3600      # 동일
ddec_arcsec = (dec - ref_dec) * 3600                       # 동일
east_px  = ew_sign * dra_arcsec  / plate_scale              # 동일
north_px = ns_sign * ddec_arcsec / plate_scale               # 동일
pa_rad   = radians(pole_pa_deg + np_ang_deg)                # 동일
dx_px = east_px*cos(pa_rad) + north_px*sin(pa_rad)           # 동일
dy_px = east_px*sin(pa_rad) - north_px*cos(pa_rad)           # 동일
```
완전히 동일하다 — 이 공유 코드 자체에 두 경로 간 차이는 없다.

### 11-2. np_ang_deg를 나머지 2개 세션까지 확대 검증

기존엔 2026-04-17·2026-03-21만 Horizons quantity-17로 대조했었다. 이번에 2026-03-28·2026-05-05(위성 세션)까지 마저 확인:
- 2026-03-28: Horizons 8.0018° vs 저장값 8.0020° (일치)
- 2026-05-05: Horizons 9.7443° vs 저장값 9.7444° (일치)

### 11-3. 비등방성(anisotropic) PSF 블러 — 새 가설, 반박됨

지금까지의 합성 테스트는 전부 등방성(isotropic) 노이즈/블러만 썼다. 실제 관측에서는 대기 시상 비대칭, 가이딩(추적) 오차, 바람 등으로 한쪽 방향으로만 더 흐려지는 비등방성 블러가 생길 수 있고, 이게 벨트 경계의 겉보기 기울기를 왜곡할 가능성을 새로 테스트했다(`experiments/verify_anisotropic_psf_bias.py`). 블러 강도(등방 대비 최대 4배 늘어남)와 블러 방향(벨트축 기준 0~120°)을 조합해 스윕했다.

**결과**: 블러를 아무리 강하게, 어느 각도로 줘도 편향은 0.87~0.88° 수준(양자화 잡음 바닥)에서 전혀 안 늘어났다. **반박됨.**

### 11-4. plate_scale·disk 중심 오차는 애초에 "회전"을 못 만든다는 걸 수학적으로 재확인

- **plate_scale**: east_px·north_px 둘 다 같은 값으로 나누므로, 오차가 있어도 벡터의 "방향"은 그대로고 "길이"만 바뀐다 — 순수 반경(radial) 오차만 생기고 회전(각도) 오차는 원리적으로 생길 수 없다.
- **disk 중심 오프셋**: 만약 이게 원인이라면, 같은 크기의 절대 픽셀 오프셋이 반지름이 클수록 더 작은 각도 편향으로 나타나야 한다(반비례 관계). 그런데 실측 그림자 데이터는 반지름 46~84px 범위에서 각도편향이 5.6~12°로 거의 일정하다 — 반비례 패턴이 전혀 안 보인다. **이 가설과 실측이 안 맞으므로 배제.**

### 11-5. "marker propagation" 가설 (세 번째 외부 검토, 매우 구체적) — 직접 구현해서 검증, 반박됨

세 번째 외부 검토가 앞의 두 라운드보다 훨씬 구체적인 메커니즘을 제시했다: 최종 de-rotated stack은 "정확히 t_center 시점의 하늘"이 아니라, **여러 원본 프레임 각각을 (원자atmospheric 공전에 맞춰) warp하고 정렬한 뒤 가중평균한 결과**다. 그런데 위성/그림자는 목성 대기와 함께 공전(co-rotate)하지 않으므로, 이 warp를 그대로 적용받으면 실제로는 존재하지 않는 위치 이동이 생긴다. 현재 tracker는 이 전파 과정을 거치지 않고 그냥 `t_center` 한 시점의 ephemeris 위치만 계산해서 마커를 찍는데(`P_center`), 실제 마커가 찍혀야 할 위치는 "각 프레임의 실제 ephemeris 위치를 동일한 warp+정렬+가중평균 파이프라인에 통과시킨 결과"(`P_propagated`)여야 한다는 것이다. 이 메커니즘은 §9-3의 "잔차가 이동방향과 거의 반대"라는 패턴을 자연스럽게 설명할 수 있고, warp의 좌표계 회전 여부(§8-5, 이미 결백 확인)와는 별개의 질문이라는 점도 정확한 지적이었다.

**방법**: 외부 검토자가 제안한 pseudocode를 그대로, **실제 production 함수**(`apply_shift_and_scale`, `spherical_derotation_warp_3d`, `quality_weighted_stack`)를 직접 호출해서 구현했다(`experiments/verify_marker_propagation.py`). 각 프레임의 등록(registration) 파라미터는 새로 측정하지 않고 이미 로그(`derotation_log.json`)에 저장된 실측값(`pre_warp_shift_dx/dy/scale`, `dt_sec`, `norm_score`, `disk_center_px`=기준 프레임 중심, `own_disk_radius_px`)을 그대로 사용했다 — 이미지 대신 그 위치에 작은 가우시안 마커를 그려서 파이프라인에 통과시키고 최종 가중치 중심(centroid)을 구했다. CV도, 실제 이미지도 쓰지 않는 순수 좌표 전파 계산이다.

**결과**: 8개 그림자 창 전부에서 `P_center`와 `P_propagated`의 차이가 **0.06~0.72px**에 불과했다 — 실제 필요한 잔차(3~15px대)보다 최소 한 자릿수 작다. **가설 반박됨.**

**왜 이렇게 작게 나오는지(부가 설명)**: 대부분의 창은 기준시각(dt=0) 앞뒤로 대칭적인 시간 간격(예: -240s, 0s, +240s)의 프레임을 사용한다. dt=0 프레임은 warp가 항등변환(정확한 위치 그대로)이고, ±240s 프레임은 서로 반대 방향으로 거의 대칭적인 "잘못된" 변위를 받는다 — 가중평균 시 이 대칭적 오차가 서로 상쇄된다. 실제로 이 상쇄가 덜 되는(프레임이 2개뿐이거나 비대칭인) 창(2026-03-21 window_01, window_02)에서 상대적으로 더 큰 값(0.72px, 0.33px)이 나온 것도 이 설명과 일치한다.

### 11-6. 현재 상태: "공통 경로"도, 이번의 구체적인 marker-propagation 가설도 뒤져봤지만 구체적 버그는 여전히 못 찾음

정리하면 이번 라운드로 배제된 것: 공유 코드 자체(완전 동일 확인), np_ang_deg(4개 세션 전부 결백), 비등방성 PSF(반박), plate_scale/disk중심 오프셋(수학적으로 회전을 만들 수 없음이 재확인), **marker propagation 불일치(실제 production 함수로 직접 계산, 0.06~0.72px로 자릿수 부족)**.

남은 것은 여전히 **"pole_pa_deg 측정치 자체가 실제 목성 이미지에서만 나타나는 어떤 특성 때문에 편향될 가능성"**뿐인데, 지금까지 시도한 모든 현실적 오염 모델(단순/현실적 limb-darkening, 오블레이트+불규칙벨트+노이즈+피팅오차, 비등방 PSF)이 전부 이걸 재현하지 못했다. 순수 formula/합성 검증으로 갈 수 있는 곳은 사실상 다 가본 것으로 보인다.

## 12. 전체 세션 커버리지 재확인 (2026-08-31 추가) — 편향이 "모든 세션"에서 확인된 게 아님

사용자가 "지금 모든 세션에서 동일한 수준의 오차가 발생하고 있는 게 맞냐"고 직접 물었다. 지금까지 §5~§11에서 쓴 8~9개 그림자 데이터 포인트는 사실 6개 세션 중 **일부 세션에서, 그것도 그 세션의 일부 창에서만** 나온 것이었다 — 나머지는 검증한 적이 없었다. 이걸 명확히 하기 위해, 그림자가 있는 4개 세션(2026-03-21/27/28, 2026-05-05)의 **아직 안 본 창 19개**를 §10-3/§11에서 쓴 것과 동일한 견고한 방법(배경 대비 3-sigma + 4가지 탐색범위 안정성)으로 마저 확인했다.

### 12-1. 전체 세션·창 커버리지 표

| 세션 | 그림자가 있는 창 수 | 신뢰할 만한 탐지 | 편향(δ) 범위 |
|---|---|---|---|
| 2026-04-17 | 10 | **7** (window_01~07) | +3.78°~+12.06° (평균 +7.93°) |
| 2026-03-21 | 5 | **2** (window_01~02) | +3.26°~+4.78° (평균 +4.02°) |
| 2026-03-27 | 5 | **0** | 측정 불가 |
| 2026-03-28 | 2 | **0** | 측정 불가 |
| 2026-05-05 | 5 | **0** | 측정 불가 |
| 2026-04-24 | 0 (on-disk 객체 자체 없음) | - | - |

새로 탐지에 성공한 2026-04-17 window_07: δ=+3.78° (예측 대비 반경 80.6px→73.2px, 총 오차 9.0px). 이걸 포함해 그림자 δ 전체(n=9): 평균 **+7.06°**, 중앙값 +8.26°, 표준편차 2.71°.

### 12-2. 탐지 실패한 13개 창은 "약한 신호"가 아니라 "신호 없음"

탐지 실패한 창들의 peak significance는 0.8~1.4-sigma로, 문턱(3.0)에 한참 못 미쳤다. 2026-03-21 window_03을 직접 픽셀 단위로 확인해보면 예측 위치 안쪽 밝기 중앙값(0.4855)과 주변 배경 중앙값(0.4875)이 거의 차이가 없었다(배경 표준편차 0.041보다도 작은 차이) — 즉 그림자 자체가 이 필터/이 시점 조건에서 거의 안 보일 만큼 약했다는 뜻이지, 탐지 방법의 결함이 아니다.

### 12-3. 결론: "+5~14°" 편향은 6개 세션 전체가 아니라 2개 세션 9개 창의 관측 범위

- **확인된 것**: 2026-04-17과 2026-03-21 두 세션, 9개 창에서는 확실히 편향이 존재한다. 다만 이 두 세션 사이에서도 크기가 다르다(평균 7.93° vs 4.02°, 거의 2배 차이) — "하나의 고정된 편향 값"이 아니라 세션마다 어느 정도 다른 크기로 나타난다.
- **모르는 것**: 나머지 4개 세션(2026-03-27, 03-28, 05-05, 04-24)에는 편향이 있는지 없는지 **이 데이터로는 알 수 없다** — 그림자 신호 자체가 탐지 문턱 아래라 검증이 안 된다. "이 세션들은 편향이 없다"라고 말하는 것도, "이 세션들도 똑같이 편향이 있다"라고 말하는 것도 둘 다 근거가 없다.
- **함의**: 앞으로 이 편향을 이야기할 때는 "위성/그림자 추적 전반의 문제"라고 일반화하지 말고, "2026-04-17·2026-03-21 세션에서 확인된, 세션마다 크기가 다른 편향"이라고 정확히 표현할 것. 원인 조사(§11) 결과도 이 두 세션의 데이터에만 기반한 것이므로, 다른 세션에서 같은 원인이 적용되는지는 별개로 검증이 필요하다.

### 12-4. 세션 내 시간 의존성 확인 — δ와 속도 둘 다 시간에 따라 변함 (사용자 질의)

사용자가 "한 세션 안에서 각도와 속도가 시간별로 다른 게 아니냐"고 직접 확인을 요청했다. 2026-04-17 세션(7개 사용 가능 창, ~92분)의 δ와 그림자 속도를 시간순으로 확인했다:

| 창 | 시간(분) | δ(°) | 속도(px/min) |
|---|---|---|---|
| window_01 | 0 | 8.71 | 1.557 |
| window_02 | 12 | 8.26 | 1.503 |
| window_03 | 24 | 12.06 | 1.456 |
| window_04 | 48 | 8.37 | 1.389 |
| window_05 | 64 | 8.71 | 1.347 |
| window_06 | 76 | 5.63 | 1.317 |
| window_07 | 92 | 3.78 | 1.274 |

- **속도**: 시간과 상관계수 **-0.996** (거의 완벽한 선형감소) — 그림자가 disk 중심으로 이동하며 생기는 원근 투영 효과로, 정상적인 물리 현상이다(버그 아님).
- **δ**: 시간과 상관계수 **-0.71**, 속도와는 +0.65~0.72, 반경과는 -0.65. 다만 이 세 변수(시간/속도/반경)가 단일 transit 안에서 서로 강하게 얽혀 있어(다 같이 변화) 어느 것이 진짜 독립변수인지 이 데이터만으로 못 가린다. 게다가 window_01(반경 75.5px, δ=8.71°)과 window_07(반경 80.6px, δ=3.78°)은 반경이 비슷한데도 δ가 2배 넘게 달라, 단순 반경 의존성 하나로는 설명이 안 된다.

**결론**: δ도 속도도 세션 내에서 시간에 따라 실제로 변한다 — "세션당 하나의 고정된 편향값"이 아니다. 다만 원인 변수가 confound돼 있어 이 관측만으로 새 메커니즘을 확정할 수는 없다.

### 12-5. "실제 극축 정렬 오차 + 목성의 고유운동" 가설 재검토 (사용자 제안) — 창 내부 프레임간 회전으로 직접 검증, 반박됨

사용자가 §5-11의 배제 근거를 다시 검토하자고 제안했다: 목성은 항성이 아니라 고유운동이 있고, 촬영 시점에 적도의 극축이 완벽히 안 맞았을 수 있다 — 이 경우 세션 전체가 아니라 **한 창(window)의 3프레임을 찍는 짧은 시간(~8분) 동안에도** 실제 field rotation이 조금씩 진행되고, 그게 스택/재측정된 pole_pa에 실제 편향을 남길 수 있다는 지적이었다. §5-11은 "창 단위 재측정값의 세션 전체 시계열이 비단조적"이라는, 잡음이 큰 다른 지표로 배제했었기 때문에, 이 지적은 정확히 다른(더 미세한) 시간 스케일을 짚은 것이었다.

**방법**: de-rotation **이전의 원본(raw) 개별 프레임** 각각(한 창당 3장, dt=-240s/0s/+240s)에서 `auto_detect_equator_pa()`로 pole_pa를 독립적으로 측정하고, dt_sec에 대한 선형 기울기(진짜 회전이면 실제 각속도로 나와야 함)를 2026-04-17의 7개 창 전부에서 계산했다. CV도, 스택된 이미지도 아닌 순수 원본 프레임 측정이다.

**결과**: 창별 기울기(deg/hour) — window_01: **+3.75**, window_02: **+7.50**, window_03: **-7.50**, window_04: **+7.56**, window_05: **-3.75**, window_06: **-7.50**, window_07: **-3.75**.

**부호가 창마다 무작위로 뒤바뀐다**(양수 3번, 음수 4번). 진짜 극축 정렬 오차라면 같은 밤, 같은 마운트, 같은 미정렬 축이므로 방향(부호)이 세션 내내 일관돼야 하는데 전혀 그렇지 않다. 각 창 안 3프레임의 pole_pa 값 차이도 0.5~2°에 불과해, 이미 특정된 측정 잡음 수준(0.5° 양자화 해상도, §5-5) 안에 있다. **가설 반박됨** — 이건 실제 회전이 아니라 순수 측정 잡음의 신호다. 두 개의 독립적 staleness(코드 버전 차이 + wavelet 왜곡)가 겹쳐 있음을 확인. 핵심 결론: **정성적 주장(위성은 CH4에서만 뚜렷, 그림자는 전 필터 개선)은 최종본에서도 유지되지만, published 수치는 자릿수 단위로 과대평가돼 있어 전부 교체 필요.** 위성 브로드밴드는 raw 기준 -0.8%~+0.9%(사실상 잡음), 그림자는 5개 필터 전부 +1.6%~+4.2%로 published 대비 한 자릿수 작음. 상세는 `paper/Paper_Fix.md` 이슈 1 "데이터 재검증 완료" 항목 참고.

### 12-9. compositing 마스크 커버리지 손실 — 측정이 아닌 알고리즘 자체에 대한 실질적 영향 (2026-09-01, 사용자 지적)

논문 그림(`derotation_flow_gradient_r`) 재현 과정에서 실제 예측좌표 기준 마커와 육안으로 확인한 실제 위치가 어긋나는 걸 보면서, 사용자가 "이게 Table 2 측정 정확도뿐 아니라 실제 compositing 마스크 커버리지에도 문제를 일으키는 거 아니냐"고 지적했다. 실제 production이 쓰는 capsule Gaussian 마스크(`_capsule_gaussian_mask`, σ = apparent_radius × coverage_scale, 기본 1.5)의 중심은 예측(ephemeris) 좌표인데, CV로 확인한 실제 신호는 그보다 몇 px 떨어져 있다 — 마스크가 가우시안이므로 실제 위치에서의 가중치는 `exp(-(오프셋/σ)²/2)`로 정량화할 수 있다.

CV로 실제 검증된(3-sigma 통과) 12개 창 전부에 대해 계산:

| 세션/창 | 대상 | 오프셋 | σ | 마스크 가중치 |
|---|---|---|---|---|
| 2026-05-05 window_02 | 위성 | 4.64px | 4.38px | **0.570** (43% 손실) |
| 2026-05-05 window_03 | 위성 | 4.33px | 4.43px | 0.620 |
| 2026-05-05 window_01 | 위성 | 4.08px | 4.36px | 0.645 |
| 2026-03-28 window_06 | 위성 | 4.11px | 4.51px | 0.661 |
| 2026-05-05 window_04 | 위성 | 3.65px | 4.41px | 0.711 |
| 2026-04-17 window_02 | 그림자 | 4.93px | 7.85px | 0.821 |
| 2026-04-17 window_03 | 그림자 | 3.82px | 7.81px | 0.887 |
| 2026-05-05 window_05 | 위성 | 1.62px | 4.33px | 0.932 |
| 2026-04-17 window_07/06/05/04 | 그림자 | 1.4~2.3px | ~7.7-7.84px | 0.956~0.984 |

**핵심**: 위성(σ≈4.3-4.5px)이 그림자(σ≈7.7-7.85px)보다 겉보기 반지름이 작아서 같은 절대 오프셋에서 훨씬 취약하다. 가장 나쁜 확인된 경우(2026-05-05 위성) 마스크 가중치가 0.57까지 떨어짐 — compositing이 진짜 신호의 43%를 놓칠 수 있다는 뜻.

**이전 프레임과의 차이**: §12-6~12-8까지는 "위치 편향 → Table 2 측정값 부정확"이라는 측정 방법론 프레임이었다. 이번 발견은 프레임 자체를 확장한다 — 편향이 크고 σ가 작은(위성) 경우엔 **측정 문제가 아니라 compositing 알고리즘 자체의 실효 강도가 약해지는 실질적 문제**다. 다만 그림자(σ가 커서 완충)와 편향이 작거나 미확인인 대부분 창(가중치 0.95+)에서는 영향이 미미해서, "일부 위성 창에 국한된 부분적 리스크"로 봐야 하며 파이프라인 전체가 항상 이런 손실을 겪는다는 뜻은 아니다.

코드 변경 없음(발견 사실만 기록) — coverage_scale을 늘려 대응하는 건 편향의 근본 원인 불명 상태에서 배경 오염 위험이라는 새 트레이드오프를 만드므로 신중한 판단이 필요. `paper/camera_ready.tex`의 "Residual Angular Placement Bias" Limitations 항목과 `paper/Paper_Fix.md` 이슈 7에 반영 완료.

### 12-10-2. 워크플로우 6개 가설 병렬 검증 — 전부 반증, 사소한 버그 2개 발견

### 12-10-3. 독립 재구현으로 ephemeris 체인 전체를 end-to-end 대조 — 결정적 결과

기존 검증은 전부 "공식 조각 하나하나를 Horizons과 대조"하는 방식이었다. 조각을 조합하는 과정(좌표계 전달, 인자 순서 등)의 버그는 이 방식으론 못 잡는다. 그래서 Skyfield를 아예 안 쓰고, **jplephem으로 커널을 직접 읽고, 수렴할 때까지 반복하는 광행시간 계산을 직접 구현하고, 광행차는 ERFA(`erfa.ab`, IAU 표준 C 구현)로 처리**하는 완전히 독립적인 재구현을 만들었다(`experiments/independent_reimpl_2026-09-01/independent_tracker.py`).

확인된 편향 세션(2026-04-17, 2026-03-21)과 대조군 세션(2026-03-27, 2026-05-05) 전부에서, 회전(pole_pa+np_ang)과 축척을 뺀 순수 "위성/그림자의 목성 중심 기준 각도 오프셋(arcsec)"을 프로덕션과 독립 구현 양쪽에서 계산해 비교했다:

```
확인된 편향 세션: 평균 차이 0.030 arcsec (0.20px @ 0.15"/px), 최대 0.059 arcsec
대조군 세션:      평균 차이 0.011 arcsec (0.07px @ 0.15"/px), 최대 0.023 arcsec
```

(주의: 첫 실행에서 ~5 arcsec/36px 차이가 나서 깜짝 놀랐으나, 원인은 비교 스크립트 자체의 버그였음 — production의 `dy_px = -north_px`는 이미지 y축이 아래로 증가하는 정당한 관례인데 비교 스크립트가 이를 반영 안 하고 그대로 빼서 Dec 부호가 반전된 것으로 나왔었음. 수정 후 위 수치로 정리됨.)

**확인된 편향(4~8°, 5~15px)보다 15~100배 작다 — ephemeris/광행시간/광행차/그림자 광선추적을 포함한 전체 위치예측 체인이 완전히 독립적인 두 번째 구현으로 end-to-end 검증됨.** 이제 다음이 전부 개별적으로도, 조합 레벨에서도 확인됨: 천체력 자체, 광행시간, 광행차, np_ang, pole_pa+np_ang 부호규약, plate_scale/disk-center(수학적으로 회전 불가), pole_pa 측정 자체(합성 대칭/비대칭 벨트 둘 다 무편향 증명). **예측(prediction) 쪽에서 남은 용의선상은 사실상 소진됨.**

### 12-10-4. 남은 가능성 — CV "정답" 측정 자체의 편향 (신규, 미검증)

예측 쪽이 전부 결백하다면, 남는 건 (a) 조합/캐싱 레벨의 소프트웨어 버그(개별 공식은 옳지만 변수 전달·순서·재사용에 실수), 또는 (b) **"정답"으로 써온 CV 측정 자체가 체계적으로 편향돼 있을 가능성**이다. (b)는 이번에 처음 제기됨 — weighted-centroid가 그림자/위성 주변의 비대칭적인 벨트·존 밝기 구조 때문에 진짜 중심에서 체계적으로 밀릴 수 있는가? 다음 세션에서 이어서 테스트할 것.

## 12-11. 돌파구: "정답"으로 써온 CV 측정 자체가 벨트/존 경계에 체계적으로 끌린다는 걸 실제 데이터로 확인 (2026-09-01)

§12-10-3에서 예측(prediction) 쪽 전체 체인이 독립 재구현으로 결정적으로 면죄된 뒤, 남은 용의선상 (b) — "CV '정답' 측정 자체의 편향" — 을 실제로 테스트했다. 이번 세션 최대 성과일 가능성이 높다.

### 12-11-1. 합성 데이터: 배경 밝기 경사가 weighted-centroid를 체계적으로 끈다 (확정)

이번 조사 전체에서 "정답" 확인에 써온 것과 동일한 로버스트 재탐지 알고리즘(box-mult 스윕, 3-sigma 문턱, 신호가중 centroid)을, 완벽히 대칭인 합성 신호(그림자=dip, 위성=bump) 위에 다양한 세기·방향의 선형 배경 경사를 얹어서 돌려봤다(`experiments/independent_reimpl_2026-09-01/test_cv_centroid_gradient_bias.py`).

- 경사가 없으면(strength=0) 편향 없음(노이즈 수준, <0.1px) — 알고리즘 자체는 무편향.
- 경사가 있으면 **그림자는 배경이 더 어두운 쪽으로, 위성은 배경이 더 밝은 쪽으로** centroid가 체계적으로 끌림.
- Monte Carlo(n=30, 경사강도 0.20): 그림자 mean_dx=-0.306±0.038(t≈-44), 위성 mean_dx=+0.301±0.039(t≈43) — 노이즈가 절대 아님, 완전히 재현 가능한 실제 편향.

### 12-11-2. 실제 벨트 경계(step) 모델로 크기 확장 (`test_cv_centroid_belt_edge_bias.py`, `test_cv_centroid_max_bias_search.py`)

완만한 선형 경사 대신 실제 벨트/존 경계에 더 가까운 tanh 스텝 모델로 바꾸고, 대비/폭/오프셋을 넓게 탐색(3-sigma 문턱을 넘는 "탐지 가능한" 범위 내에서 최대치 탐색):

- Ganymede 그림자 스케일(r_px≈10.4): 최대 4.3px, **위성** 스케일: 최대 **7.0px** (확인된 실제 편향 5~15px의 43~70%!)
- Io 그림자/작은 위성 스케일(r_px≈6.1): 최대 ~2.0px (약 20%)

### 12-11-3. 결정적 검증: 실제 이미지에서 확인된 편향 창들 근처에 진짜 벨트 비대칭이 있는가

가장 중요한 단계 — 합성 실험이 아니라 **실제로 확인된 편향을 가진 12개 창의 진짜 이미지**에서, 예측 위치의 배경 annulus를 "CV 보정 방향 쪽 절반" vs "반대쪽 절반"으로 나눠 밝기를 비교했다(`experiments/independent_reimpl_2026-09-01/check_real_belt_edge_near_bias_windows.py`). 합성 실험에서 확립된 방향 규칙(그림자는 어두운 쪽으로, 위성은 밝은 쪽으로 끌림)과 비교:

```
전체 60행 중 47행(78%)이 예측 방향과 일치
위성만 보면: 30/30(100%) 전부 일치 — 우연이라 보기 매우 어려움
그림자는 혼재(2026-04-17 window_02/03는 불일치, window_06/07은 대체로 일치)
```

**위성 케이스는 예외 없이 전부, CV가 "실제 위치"라고 찾아낸 방향이 정확히 그 창의 국소 배경이 더 밝은 방향과 일치한다.** 이건 "위성 위치예측이 5px 안팎 틀렸다"가 아니라 **"CV 검증 방법 자체가 밝은 배경 쪽으로 체계적으로 끌려서, 정확한 예측을 '틀렸다'고 잘못 판정했을 가능성이 매우 높다"**는 뜻이다.

### 12-11-4. 재해석 — 이슈 7 전체에 대한 함의

- **위성**: 독립 재구현(§12-10-3)으로 예측 자체가 <0.4px 정밀도로 정확함이 확인됐고, 이번엔 "확인된 편향"이라 불러온 것 자체가 CV 측정 아티팩트로 설명될 가능성이 매우 높다는 직접 증거(100% 방향 일치)까지 나왔다. **위성 트래킹은 실제로는 논문이 주장하는 수준으로 정확할 가능성이 높다.**
- **그림자**: 증거가 더 약하고 혼재돼 있다 — 일부 창은 벨트-끌림으로 설명되지만(window_06/07), 일부는 안 된다(window_02/03). 그림자는 순수 벨트-끌림 외에 다른 요인(또는 진짜 트래커 편향)이 남아있을 가능성이 있다.
- **크기 검증 완료 (2026-09-01 후속, 사용자 요청) — 위 낙관적 결론을 상당 부분 철회**: §12-11-3의 방향-일치 확인은 "annulus를 근/원 절반으로 나눈 중앙값 비교"라는 완화된 기준이었다. 실제 탐지 알고리즘 전체(box-mult 스윕 + 3-sigma + weighted centroid)를 그대로 돌려서 크기까지 정량 검증했다(`quantify_belt_bias_magnitude.py`): 각 창의 실제 배경(annulus에 평면 피팅)과 실제 신호 세기(1r 내 실측 깊이/높이)를 그대로 써서 완벽히 대칭인 합성 신호를 주입한 하이브리드 이미지를 만들고, Monte Carlo 20회 평균으로 로버스트 재탐지를 돌렸다.
  - **크기**: 배경 기울기 메커니즘 혼자서는 실제 관측된 오프셋의 **평균 10~20%만 설명**(위성 n=6 평균 11.8%, 그림자 n=30 평균 20.6%) — 중앙값 기준도 비슷(9.3%/20.2%). **나머지 80~90%는 이 메커니즘으로 설명 안 됨.**
  - **방향**: 36행 중 19행(53%)만 완화 기준(cos_sim>0.5)을 통과 — §12-11-3의 78%/100%보다 훨씬 약함. 특히 2026-04-17 window_06/07은 방향이 오히려 반대(cos_sim 음수)로 나옴.
  - 위성은 실제 신호 세기로 하이브리드를 만들면 브로드밴드(IR/R/G/B) 전부 20회 시행 전부 탐지 실패(신호가 원래 너무 약함, 기존 발견과 일치) — CH4만 탐지되고, 그마저도 방향/크기 설명력이 크지 않음.
- **결론 (수정)**: 배경 밝기 기울기가 CV 측정을 체계적으로 끄는 건 **실재하는, 재현 가능한 현상**이지만(§12-11-1/2에서 노이즈 아님을 통계적으로 확정), 크기 기준으로는 확인된 편향의 **부분적(10~20%) 기여자**일 뿐 **주된 원인은 아니다.** §12-11-3의 "78%/100% 방향 일치"는 완화된(덜 엄격한) 판정 방식의 결과였고, 실제 탐지 알고리즘 전체로 재현하면 훨씬 약해진다 — 초기 낙관적 해석은 과장이었음을 인정한다. 이슈 7의 근본 원인은 **여전히 대부분 미상**이며, 이번 라운드는 "실재하지만 부분적인 기여 요인 하나를 정량적으로 특정"한 것으로 정리한다.

## 12-12. 새로운 실마리: 벨트-기울기 pole_pa vs 타원-피팅 pole_pa — 두 독립 측정법이 체계적으로 다르고, 타원 쪽이 대체로 더 정확함 (2026-09-01)

사용자가 "원인을 찾아봐 달라고 한 거 아니냐"며 재차 요청. §12-11의 CV-아티팩트가 부분적(10-20%) 기여에 그친다는 걸 인정한 뒤, 아직 안 짚어본 걸 하나 찾았다: **pole_pa 측정법이 원래 두 가지**다 — 지금까지 계속 테스트해온 벨트 밝기 기울기 방식(`auto_detect_equator_pa`, 실제 사용 중)과, 논문에도 서술된 원반 타원 모양 기반 방식(`equator_pa_from_disk_ellipse`, 현재 코드에서는 벨트 방식이 예외를 던질 때만 쓰이는 폴백이라 사실상 거의 항상 우회됨). 이 둘을 지금까지 서로 대조해본 적이 없었다.

확인된 편향 9개 창(2026-04-17 window_01-07, 2026-03-21 window_01-02) 전부에서, 각 창의 실제 이미지에 대해 자기완결적으로(같은 이미지에서 disk 중심 재검출 + 두 방법의 pole_pa 계산 + 신선한 CV 재탐지) 두 방법을 직접 비교했다(`test_ellipse_vs_belt_pole_pa.py`):

```
ellipse-fit closer to CV ground truth in 8/9 windows
mean belt_off=8.54px  mean ellipse_off=6.86px  (약 20% 감소)
```

두 방법이 주는 pole_pa 값 자체도 체계적으로 다르다(대부분 2~5° 차이, 거의 항상 같은 방향 — 타원 쪽이 0에 더 가까움, 기존에 파악된 "필요 보정 방향"과 일치). 예외는 2026-04-17 window_04 하나뿐.

**중요한 방법론적 지점**: 이건 CV 데이터에 피팅한 게 아니다 — 둘 다 코드에 이미 있는, 순수 기하/광도 기반의 독립적인 측정법이고, "어느 쪽이 더 정확한가"를 비교했을 뿐이다([[feedback_no_cv_offset]] 원칙 위배 아님).

**한계**: 이것도 완전한 답은 아니다 — 타원 방식을 써도 평균 6.86px 오차가 남는다(원래 편향 5-15px 대비 부분적 개선). §12-10의 벨트-비대칭 실험(수학적으로 gradient histogram 피크가 안 움직임을 증명)이 어떻게 이것과 공존하는지도 아직 설명 안 됨 — 벨트 asymmetry 자체가 아니라 다른 메커니즘(예: 벨트 gradient 방법이 wavelet 스케일 선택에서 limb-darkening에 여전히 취약하다는 기존 "OPEN QUESTION" 주석, 또는 벨트 구조의 경도 방향 비대칭 등)일 가능성. 다음 단계 후보: (1) 왜 두 방법이 체계적으로 다른지 원인 규명, (2) window_04가 왜 예외인지 확인, (3) 실제로 primary pole_pa 소스를 바꾸거나 두 방법을 결합하는 게 타당한지 판단.

## 12-13. 타원-피팅 pole_pa를 실제 프로덕션에 통합 테스트 — 격리 테스트와 정반대 결과, 되돌림 (2026-09-01)

§12-12에서 "타원 피팅이 8/9 창에서 더 정확하다"는 결과가 나왔지만, 사용자가 "전체 데이터에 실제로 적용해서 전체값을 보자 — 어차피 데이터 전체가 원리에 대한 샘플이니까"라고 요청. `pipeline/steps/derotate_stack.py`의 `pole_pa_for_tracker` 소스를 실제로 `equator_pa_from_disk_ellipse()`로 바꾸고, 6개 세션 전체를 처음부터 다시 재처리(`experiments/reprocess_2026-09-01_ellipse_pa/`)해서 확인했다.

**결과가 정반대로 나왔다.** 같은 9개 확인된 편향 창을 실제 프로덕션 출력으로 다시 보니:

```
window_02: 4.93px → 9.61px (악화)
window_03: 3.82px → 9.46px (악화)
window_04: 1.42px → 9.05px (대폭 악화)
window_05: 1.93px → 8.76px (대폭 악화)
window_06: 2.24px → 8.75px (대폭 악화)
window_01, 07, 2026-03-21 둘 다: CH4 앵커링 신뢰도 자체가 무너짐
```

직접 확인해보니(2026-04-17 window_02), CV가 찾은 "진짜" 위치는 old/new 실행에서 거의 동일했다(214.49,114.29 vs 214.58,114.22 — 0.1px 차이, 즉 실제 신호 자체는 그대로임을 재확인). 그런데 예측 위치만 타원 방식으로 바뀌면서 진짜 위치에서 오히려 멀어졌다.

**원인**: §12-12의 격리 테스트(`test_ellipse_vs_belt_pole_pa.py`)는 한 이미지에서 직접 disk 중심을 검출하고 그 자리에서 바로 pole_pa 두 방식을 비교했지만, **실제 프로덕션 코드는 pole_pa를 "선호 필터"(우선순위: IR→R→G→B→CH4) 이미지에서 딱 한 번만 측정하고, 그 값을 각 필터가 "자기 자신의" disk 중심으로 따로 검출한 좌표에 적용**한다(`_apply_satellite_composite` 내부). 격리 테스트는 이 필터-간 조합을 재현하지 못했다 — 정확히 어느 지점이 문제인지는 특정 못했지만, 결과가 명백히 반대로 나온 이상 프로덕션 코드는 즉시 원복했다.

**교훈**: 아무리 신중하게 만든 독립 재구현이라도, 실제 통합 코드 경로에서 재검증하기 전까지는 결론을 신뢰하면 안 된다. 사용자의 "전체 데이터로 실측해보자"는 요청이 정확히 이 실수를 잡아냈다 — 격리 테스트 결과만 믿고 코드를 바꿨다면 실제로는 편향을 악화시켰을 것이다.

**되돌림 완료**: `pipeline/steps/derotate_stack.py`의 `pole_pa_for_tracker`는 원래의 벨트-기울기(`auto_detect_equator_pa`) 방식으로 복원됨. 157개 테스트 통과 확인. `experiments/reprocess_2026-09-01_ellipse_pa/`는 이 회귀를 보여주는 증거로 남겨둠(diagnostic only, 커밋 대상 아님).

**현재 상태**: 이슈 7은 여전히 미해결. 지금까지 시도한 완화책(프레임 불일치 수정 8-10% 개선, CV 아티팩트 10-20% 부분 기여, 타원-피팅은 반증) 중 실제로 검증되어 남아있는 건 프레임 불일치 수정뿐이다. 나머지는 격리 테스트에서만 유효해 보였거나 부분적 기여에 그쳤다.

## 13. 재개 시 참고사항

- **이미 배제된 것으로 취급하고 재검증 낭비하지 말 것**: `+ np_ang_deg` 부호(§8-1에서 12개 시나리오로 확정), warp 자체의 좌표계 회전 여부(§8-5에서 확정, warp는 무죄), 노출 타임스탬프 의미(§9-4, 사용자가 캡처-중앙 기준이라 확인), **촬영 PC 시계의 절대 오차(2026-10-24, 사용자 확인: 촬영 당시 Windows 시간 서비스 켜짐 + 온라인 상태 → 시계는 UTC에 동기화돼 있었음)**, 공유 픽셀투영 코드 자체의 body/shadow 불일치(§11-1, 완전 동일 확인), np_ang_deg(§11-2, 4개 세션 전부 확인), 비등방성 PSF 블러(§11-3, 반박), plate_scale·disk중심 오프셋이 회전을 만드는 경로(§11-4, 수학적으로 불가능 + 실측 반비례패턴 부재로 배제), **marker propagation 불일치(§11-5, 실제 production 함수로 직접 계산 — 0.06~0.72px로 자릿수 부족해서 배제)**.
- **새로 확인된, 아직 원인 미상인 구체적 단서**: 그림자 잔차가 객체 자신의 이동방향과 8/8 지점에서 150~177°(거의 반대)로 정렬됨(§9-3, 이 측정값 자체는 유효함) — "몇 분의 시간 지연"처럼 보이지만 노출 타임스탬프·quality-weighted 평균시각·marker propagation·촬영 PC 시계 오차 넷 다 원인이 아님이 확인됐다. 이 정렬 자체는 진짜 관측값이니 향후 재개 시 "왜 이런 패턴이 생기는가"는 여전히 유효한 질문으로 남겨둘 것 — 다만 지금까지 시도한 시간/warp 계열 설명은 전부 소진됐다.
- **방향은 여전히 유효, 구체적 버그는 미발견**: CH4 한정 재분석(§10-5, n=5로 확대해 §10-6에서 통계적으로 재평가)에서 위성도 그림자와 같은 부호의 disk-중심-기준 각도 편향을 보이는 경향이 있어(통계적으로 0은 배제되나 정확한 크기는 불확실), `_shadow_pos_skyfield`(그림자 전용)보다 **위성·그림자가 공유하는 `pole_pa_deg + np_ang_deg` → 픽셀 투영 경로, 또는 pole_pa_deg 측정치 자체**에 원인이 있을 가능성이 여전히 더 높다고 본다. 그런데 §11에서 이 공통 경로를 직접 파봤지만(코드 대조, np_ang 전수검증, 비등방 PSF, plate_scale/disk중심 수학적 논증, marker propagation) 전부 결백으로 나와, **구체적 버그는 여전히 못 찾았다.** 순수 formula/합성 검증으로 시도해볼 만한 항목은 사실상 소진된 것으로 보인다 — 재개한다면 새로운 종류의 검증 방법(예: 실제 다른 관측 장비/세션의 데이터, 또는 WinJUPOS 등 독립 도구)이 필요할 가능성이 높다.
- 이 8개 shadow 오차 데이터로 pole_pa 보정을 **피팅**하는 시도는 절대 금지 — CV 기반 보정 금지 원칙(위성/그림자 좌표를 CV로 측정한 값에 맞춰 보정하지 않는다)에 정확히 위배된다. 진단용으로만 쓸 것.
- 관련 코드 주석: `pipeline/modules/satellite_tracker.py`의 `_get_positions_skyfield()` 내부 "OPEN QUESTION" 주석(2026-08-10 최초 작성, 2026-08-31 이번 조사 결과로 갱신).
- 관련 문서: `docs/technical_en.md` / `docs/technical_ko.md`의 "Shadow Position Algorithm" 섹션.
- 외부 검토를 받을 때는 **반드시 현재 HEAD의 실제 코드를 새로 첨부**할 것 — 이번 라운드에서 지적된 4건 중 3건(CV 자동보정, `pole_pa_for_tracker` 수정 여부, `tracker_flip_ns` fallback)이 이미 고쳐진 구버전 코드 기준이라 무의미했다.

## 14. 반지름 정의 불일치 버그 발견·수정 (2026-09-02, CV 기반 위치보정 기능 검증 중 발견)

**배경**: CH4 기반 위성/그림자 CV 좌표보정 기능([[project_cv_position_refinement_feature]])을 실데이터로 검증하던 중, Table 2 재계산을 요청받아 6개 세션을 전부 새로 재처리했다. 이 과정에서 2026-04-24 Ganymede(위성) 행이 **통째로 사라지는** 것을 발견했다 — 예전엔 합성됐던 창이 현재 HEAD 코드로는 disk 밖으로 판정되어 위성 합성 자체가 스킵됐다.

### 14-1. 원인: plate_scale용 반지름과 on-disk 판정용 반지름이 서로 다름

`compute_session_disk_radius()`(세션 전체의 plate_scale 계산용)는 `refine_disk_radius_for_plate_scale()`(Minnaert-law 광도프로파일 피팅, 0dd67d1 커밋에서 도입 — `find_disk_center()`의 raw 반지름이 한계-어두워짐 때문에 실제 디스크보다 7~16% 작게 나온다는 게 이미 알려진 문제였음)로 **보정된, 더 큰** 반지름을 쓴다. 반면 `_apply_satellite_composite()`가 "이 위성이 디스크 안에 있는가"를 판정하는 경계값은 그 필터 자신의 `find_disk_center()` **raw(미보정)** 반지름을 그대로 썼다.

plate_scale(arcsec/px)은 반지름에 반비례하므로, plate_scale이 더 큰(보정된) 반지름 기준으로 계산되면 같은 실제 각거리라도 픽셀 거리(dist_px)가 반지름 비율만큼 **부풀려져서** 나온다 — 그런데 그 부풀려진 dist_px를 raw(더 작은) 경계값과 비교하니, 실제로는 디스크 안에 있는 근접-limb 천체가 계통적으로 off-disk로 오판정된다.

**직접 재현·검증** (2026-04-24 window_01, Ganymede):
- raw 반지름(98.8px) 기준 plate_scale → dist=92.5px → **on-disk** (여유 6.3px, 과거 문서의 "92px vs disk_r 98.8px, 여유 6.8px"와 일치)
- 세션이 실제로 쓰는 보정된 반지름(110.9px, raw 대비 +12~16%) 기준 plate_scale → 동일한 물리적 위치인데 dist=103.8px → **off-disk** (raw 경계 98.8px 초과)

이 세션의 반지름 보정폭(raw 98.8px → 보정 110.9px, +12.3%)이 docstring이 명시한 "~7-10% underestimate"보다 다소 컸던 것도 확인됨(범위이지 상한이 아니라 자연스러운 세션간 편차로 판단).

### 14-2. 수정

`_apply_satellite_composite()`의 on-disk 판정/오프셋 재계산에 쓰는 반지름만 `refine_disk_radius_for_plate_scale()`로 별도 보정(`disk_sr_pos`/`ch4_sr_pos`, `pipeline/steps/satellite_composite.py`). warp 지오메트리(`warp_params["disk_r"]`), `polar_eq_ratio`, `disk_centers` 로그 등 **다른 용도의 raw 반지름은 그대로 유지** — 이 버그가 영향을 준 건 순수하게 "plate_scale 계산에 쓴 반지름"과 "경계 판정에 쓴 반지름"의 불일치뿐이므로, 수정 범위를 거기에만 국한했다(워프 지오메트리를 잘못 건드리면 이미 검증된 다른 동작을 깨뜨릴 위험이 있음).

### 14-4. 이 발견이 회전편향(δ, 각도) 미스터리와 어떤 관계인가

**주의**: 이 버그는 디스크 중심으로부터의 **반지름 방향(거리)** 오차이지, 이번 조사 내내 다뤄온 **각도(rotational, δ)** 편향과는 다른 성분이다. 이 버그 하나로 §1~13의 회전편향 미스터리가 해결됐다고 볼 근거는 없다 — pole_pa 자체의 각도 계산에는 관여하지 않기 때문. 다만:
- 반지름 방향 오차와 각도 방향 오차가 함께 있으면 "총 오차(px)" 지표(§10-5 표 등에서 쓴)가 실제보다 커 보였을 가능성은 있다 — 인과관계를 다시 따로 검증하지 않았으므로 단정하지 않는다.
- 이 버그는 근접-limb(디스크 경계 근처) 천체에서만 유의미하게 나타난다(경계에서 먼 천체는 반지름이 조금 달라져도 on/off-disk 판정 자체는 안 바뀜) — §1~13에서 다룬 확인된 편향 창들(2026-04-17, 2026-03-21)이 근접-limb이었는지는 별도 확인이 필요.
- **결론**: 이건 진짜 발견된, 수정된, 검증된 버그이지만 "회전편향의 원인을 찾았다"는 뜻은 아니다. §12의 "90%는 원인 불명" 결론은 그대로 유효하다.
